# ClassOrbit 改进状态与后续路线

这份路线以“单教师、小学课堂、轻量 Docker 部署”为边界。当前继续采用 Go 单体、React 前端和单个 SQLite 数据库：积分、签到与名单操作需要事务一致性，拆分服务或数据库只会增加部署和备份成本。

## 本轮已经完成

### 考勤与课表

- 考勤列表改为游标分页，先加载场次摘要，选中后再加载学生明细；正在查看的活动场次每 5 秒刷新一次。
- 考勤记录可一键移入回收站，进行中的场次删除后立即停止签到；支持恢复和二次确认后的永久删除。
- 场次保存班级名、学号和姓名快照，修改或软删除班级、学生不会污染历史考勤。
- 后端按服务器时间匹配学期、节次、常规课表、被占课和临时换课，返回当前课时建议。
- 教师必须在弹窗中核对班级、课程和上课时间，并勾选人工确认，才能开放签到。
- 按用户要求不实现动态口令和二维码签到。

### 数据结构与可恢复性

- 引入追加式版本迁移表，后续结构变更不再继续堆叠零散启动 SQL。
- 班级和学生使用软删除；考勤使用独立回收站；积分撤销写入反向流水，不修改或删除原始积分事件。
- 重要删除、恢复、积分调整、密码修改、备份恢复和报表导出写入操作审计。
- 在线备份使用 SQLite `VACUUM INTO` 生成一致性单文件；上传恢复前执行来源表检查和完整性检查，并生成恢复前安全备份。
- 默认每天自动备份一次并保留 14 天；恢复前安全备份不受自动清理规则影响。
- 支持班级名单、积分流水和日期范围考勤 Excel 报表。

### 性能、安全与工程质量

- 班级名单开放接口使用一次联表查询，消除按班级逐个读取学生的 N+1 查询。
- 名单接口支持私有 ETag 条件请求和 `304 Not Modified`，减少重复传输。
- SQLite 启用 WAL、外键和 busy timeout；当前单写入进程保持一个数据库连接，避免无意义的写锁竞争。
- 登录、学生签到和名单接口加入内存限速；签到额度考虑了整班共享 NAT 地址的集中请求。
- HTTP 服务补充读取/写入/空闲超时、安全响应头、数据库健康探测和优雅停机。
- 前端按页面懒加载；GitHub Actions 执行前端组件测试、生产构建和 Go API 测试后，才发布多架构镜像。
- 当前 npm 依赖审计为 0 个已知漏洞。

## 下一阶段可选项

这些功能有价值，但不应在没有明确使用场景时继续扩大系统复杂度。

| 优先级 | 建议 | 适用条件 |
| --- | --- | --- |
| P1 | 增加班级/学生归档管理页 | 经常误删名单，且希望在界面中主动恢复，而不是重新创建或导入时恢复。 |
| P1 | 增加异地备份任务 | 服务器磁盘本身可能损坏；把每日备份同步到 NAS、S3 兼容存储或另一台主机。密钥应由部署平台管理。 |
| P1 | 补充正式版本发布流程 | 准备长期公开维护时，选择许可证，并加入变更日志、Issue 模板和升级说明。 |
| P2 | 增加班级学期统计 | 确实需要出勤率趋势、积分分布和学生阶段报告时，基于现有快照与流水聚合。 |
| P2 | 增加可配置备份时间 | 只有默认“容器启动时检查、之后每 24 小时”不符合运维窗口时再做。 |
| P2 | 增加前端端到端测试 | 页面交互继续扩展后，用 Playwright 覆盖“建班 → 导入 → 发起签到 → 学生签到 → 结束”的浏览器流程。 |

## 明确暂缓的架构改造

- 不引入 SSE/WebSocket：活动考勤当前只轮询一个场次，5 秒间隔足以满足课堂反馈，长连接会增加代理和断线恢复复杂度。
- 不引入 Redis、消息队列或微服务：单教师系统没有跨节点协调需求。
- 不迁移 PostgreSQL：SQLite 的事务、备份和单写入模型更适合当前部署。只有出现多实例写入或持续写锁等待时才重新评估。
- 不加入动态口令或二维码：这是明确排除的产品方向。

## 性能基线建议

如果后续数据量明显增长，先准备不含真实学生信息的压测数据，再决定优化方向。建议基线包含 50 个班、2500 名学生、10 万条积分流水和 3000 个考勤场次，并记录：

- 班级列表、积分台和考勤历史的 P50/P95 延迟。
- 100 名学生在一分钟内集中签到的成功率与 P95 延迟。
- 名单接口首次 `200` 的响应体积，以及 ETag 命中后 `304` 的延迟。
- 容器冷启动时间、稳定内存占用、镜像体积。
- 数据库备份、完整性校验与恢复耗时。

只有指标持续超过课堂可接受范围时，再针对慢查询、索引、缓存或数据库架构做定向调整。
