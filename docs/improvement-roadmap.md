# ClassOrbit 改进路线建议

这份路线以“单教师、小学课堂、轻量部署”为边界。当前架构没有必要拆成微服务；在真实数据证明 SQLite 或单进程成为瓶颈前，保持单体更容易部署和备份。

## 已完成的低风险性能优化

- 考勤管理首次加载历史列表，之后每 5 秒只刷新当前正在查看的活动场次，避免反复下载最多 100 个历史场次及全部学生明细。
- 班级名单开放接口由“先查班级、再逐班查学生”改为一次联表查询，班级数量增加时不会产生 N+1 查询。
- SQLite 已启用 WAL、外键、5 秒 busy timeout，并使用适合当前写入模型的单连接。
- 考勤列表使用两次固定查询批量组装场次和明细，静态资源使用长期缓存，前端页面按模块懒加载。

## P0：公开部署前建议完成

### HTTPS 与网络边界

在应用前增加 Caddy 或 Nginx，自动申请 HTTPS 证书，只向公网开放 80/443。应用的 8080 端口应只对反向代理或可信网络开放。

### 登录和公开接口限速

教师登录、学生签到和名单集成接口应增加基于 IP/账号的限速。可以优先在反向代理层实现，避免为单进程应用引入复杂的分布式限流组件。

### HTTP 服务超时和安全响应头

用 `http.Server` 配置 `ReadHeaderTimeout`、`ReadTimeout`、`WriteTimeout` 和 `IdleTimeout`，并补充 `X-Content-Type-Options`、合理的 CSP、Referrer Policy 等响应头。

### 一致性备份

不要在 WAL 模式运行期间只复制主数据库文件。建议提供“停止服务后打包数据卷”脚本，或在后端增加 SQLite Online Backup/VACUUM INTO 管理功能，并定期做恢复演练。

### 历史考勤快照

考勤明细当前仍关联实时学生表。删除或改名学生会改变历史记录。建议在考勤明细中保存当时的学号和姓名快照，学生改为软删除，从而让历史考勤真正不可变。

## P1：质量和维护性

- 把后端按 `auth`、`attendance`、`schedule`、`integration` 拆分文件或包，并使用带版本号的数据库迁移。
- 为前端增加 Vitest 与 React Testing Library，至少覆盖登录门禁、积分乐观更新、考勤删除和导航未保存提示。
- 增加端到端测试，验证“创建班级 → 导入名单 → 开放签到 → 学生签到 → 关闭场次”的完整流程。
- 健康检查增加数据库探测，并加入优雅停机，确保容器退出前完成正在执行的事务。
- 为删除班级、删除学生和删除考勤增加操作审计，记录教师、时间和对象，而不是只写普通访问日志。
- GitHub 仓库补充许可证、贡献指南、Issue 模板和版本变更记录；许可证需要项目所有者自行选择。

## P2：数据量增长后再做的性能优化

以下优化应在监控或压测证明存在瓶颈后实施：

| 现象 | 建议 |
| --- | --- |
| 考勤历史超过数千场 | 改为基于游标的分页，只在展开场次时加载学生明细。 |
| 积分流水超过十万条 | 增加按时间范围查询、归档策略，并用 `EXPLAIN QUERY PLAN` 核对索引。 |
| 名单接口响应很大 | 增加 ETag/版本号和条件请求；由反向代理启用 gzip 或 Brotli。 |
| 多个页面重复读取课表 | 加入短时内存缓存，课表或设置变更时主动失效。 |
| SQLite 写等待明显增加 | 先缩短事务、检查慢查询和磁盘性能；确有多写入节点需求时再评估 PostgreSQL。 |
| 前端首屏变慢 | 在 CI 中生成 bundle report，按实际体积拆包，不按文件数量猜测优化。 |

## 建议建立的性能基线

准备一份不含真实学生信息的压测数据，至少包含 50 个班、2500 名学生、10 万条积分流水和 3000 个考勤场次，然后记录：

- 教师班级列表和积分台接口的 P50/P95 延迟。
- 活动考勤轮询响应大小和数据库查询时间。
- 100 个学生在一分钟内集中签到时的成功率与 P95 延迟。
- 容器冷启动时间、内存占用和镜像体积。
- 数据库备份与恢复耗时。

只有基线持续变差或超过实际课堂需求时，才引入更复杂的缓存、队列或数据库。
