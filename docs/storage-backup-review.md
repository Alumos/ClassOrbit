# v1.8.4 存储与备份审查（2026-09-18）

本轮覆盖数据入口、SQLite 查询/迁移、备份生成、下载、自动保留、上传恢复、故障回滚、凭证和网页缓存。检查使用合成数据及旧版本生成的数据库，未接触生产学生数据。

## 已确认并修复

| 环节 | 原问题 | 修复 |
| --- | --- | --- |
| 数据库启动 | 每次打开都执行历史字段探测、考勤回填及课表修补 | schema ≥ 3 只执行未应用的追加迁移；拒绝未来 schema |
| 索引 | 网页 public_id UNIQUE 和审计 INTEGER PRIMARY KEY 已有索引，又建了重复索引 | 迁移 4 删除两项冗余，增加班级/删除状态/ID 考勤分页索引 |
| 班级读取 | 列表与单项查询重复；新增索引会干扰当前场次查询的选路 | 共享查询和解码，当前场次指定已有活动场次唯一索引 |
| 考勤报表 | `date(session_at)` 妨碍日期索引范围查找 | 改用起始日期含、结束日期次日不含的范围 |
| 在线备份 | VACUUM INTO 占用业务唯一连接，其他查询需等待 | 独立只读 WAL 连接生成已提交数据快照；文件 0600 并同步落盘 |
| 恢复预检 | 只查五张表和 quick_check，遗漏外键与网页源损坏 | 检查全部核心表、对应版本新增表、外键、未来版本、网页关联、压缩源 SHA-256、ZIP 解压校验和入口 |
| 恢复切换 | 忽略 checkpoint 的 busy 结果，替换后才撤销凭证且忽略错误 | 检查 checkpoint 状态；候选库先原子撤销会话/扫码凭证并写审计，再替换 |
| 回滚 | 直接移动安全副本，部分错误未检查 | 从安全副本复制到临时文件并同步落盘后原子替换，保留安全副本 |
| 网页缓存 | 清理失败时数据库已替换，却返回恢复失败 | 缓存失败记日志；数据恢复成功状态、凭证撤销不受影响 |
| 自动备份 | 当天文件存在即跳过，即使 SQLite 文件已损坏 | 先验证有效性，不通过则重新生成；保留期不删除恢复前副本 |
| 上传/UI | 512MB 上传仅允许 20 秒；前端没有大小预检 | 读取超时 5 分钟，前端 512MB 校验，成功后清除 Cookie 并重新登录 |

没有增加通用缓存、连接池、服务或第二套数据模型。仍使用一个业务数据库连接，备份临时打开只读连接。没有保留测试中出现退化的聚合 JOIN 和强制物化分页改写。

## 恢复链路

1. 教师确认恢复并上传文件（最多 512MB，文件内存缓冲 8MB）。恢复期间暂停其他请求。
2. 在临时文件检查 SQLite、核心表、外键与版本，应用所需迁移，验证可恢复的网页源。
3. 在原数据卷生成当前数据库安全副本。
4. 候选库事务内删除登录会话和扫码挑战、写入审计；确认候选和在线库 checkpoint 成功。
5. 关闭在线库并原子替换；重开失败时从安全副本回滚，不消耗安全副本。
6. 更新网页访问注册表、清理缓存、清除 Cookie；使用备份中的账号重新登录。缓存缺失时从数据库压缩源重建。

## 验证

- HTTP 完整闭环：下载备份后修改积分、软删除名单，再恢复；逐表核对账号、班级、学生、积分历史、考勤回收站/明细、课表/换课、设置、导航和网页源；再次重启核对。
- 安全副本保留恢复前的新修改；恢复审计存在，旧会话和已批准的扫码凭证全部撤销。
- 缺少积分表、孤立外键、未来 schema、缺失网页源、损坏压缩源、凭证撤销失败均拒绝恢复，在线库和原会话保持可用。
- 模拟无法创建安全副本、无法清理缓存、checkpoint busy、数据库替换后安全回滚；确认各阶段状态。
- 独占业务写连接并写入尚未提交的数据时，备份仍能完成，且不包含未提交内容。
- 当天损坏 SQLite 备份重新生成；旧自动备份清理不影响恢复前安全副本。
- v1.8.3 实际程序创建数据后切换新版：账号/会话、名单、积分、考勤、课表、设置、网页、缓存重建、旧备份恢复、重复重启与 SQLite 完整性通过。
- 前端恢复文件上传、成功后退出登录、超限拒绝测试；完整 Go 测试、race、vet 和前端测试/生产构建通过。

## 性能测量

Apple M1 / macOS，50 班、2500 学生、10 万积分流水、3000 场考勤及 15 万考勤明细。v1.8.3 和本轮使用相同基准，顺序运行三次，表中为中位数；这些是本机数据库调用耗时，不是生产 HTTP 延迟。

| 操作 | v1.8.3（ms） | 本轮（ms） |
| --- | ---: | ---: |
| 班级列表 | 0.681 | 0.699 |
| 单班名单 | 0.112 | 0.107 |
| 全校名单接口数据 | 4.005 | 3.955 |
| 考勤首页 | 1.696 | 1.788 |
| 按班级筛选考勤 | 1.479 | 1.098 |
| 按日期筛选考勤 | 2.037 | 2.213 |
| 学生积分历史 | 0.088 | 0.091 |
| 数据库重开（单独测量） | 0.888 | 0.602 |
| 完整 SQLite 备份 | 84.203 | 86.014 |

按班级筛选考勤约减少 26% 耗时，数据库重开约减少 32%。其余查询无数量级变化，保留实测波动，不声称全系统普遍加速。备份总耗时基本不变，主要收益是业务连接不再被备份独占。基准已保存在 `backend/storage_bench_test.go`。

```bash
go test ./backend -run '^$' -bench BenchmarkStorage -benchtime=300ms -count=3
```

## 升级与边界

- 原 `/app/data` 卷、数据库文件名、业务表和网页内容版本保持不变，迁移 4 只调整索引。无需重新导入或上传。
- 同卷自动备份不能抵御磁盘/主机损坏；仍需把已完成备份复制到其他设备。项目没有配置异地备份目的地。
- 恢复上限 512MB，上传允许 5 分钟；反向代理也须允许对应请求体和超时。超过上限的库不能直接通过网页恢复。
- 测试没有模拟物理断电、磁盘硬件故障或生产服务器实际 Docker 切换；这些不能由单元测试保证。故障时安全副本位于数据卷 `backups/`。
